# 插件规范

> JianShanAgent · 核心 · 文档

JianShanAgent 的东西分三层：**核心**只懂 MediaWiki 和 QQ；某个平台、某个站特有的东西是**插件**；
把核心和插件拼起来、指向某一个 wiki 的是**实例**。这份文档规定各层怎么取名、插件的目录里放什么、
怎么让核心找到它、文档怎么写。能用程序查的部分有自检（见最后一节），每个插件仓库的测试里跑一次。

## 1. 分层和命名

| 层 | 是什么 | 仓库名 | 发行包（`pyproject.toml` 的 `name`） | Python 包 | 插件 id | 配置名 |
|---|---|---|---|---|---|---|
| 核心 | 机器人本体、自带的功能插件、管理后台、部署工具 | `agent-core` | `jianshanagent` | `jianshanagent` | — | `app`、`core.*`、`gateway.*` |
| 功能插件 | 机器人会做的一件事 | `plugin-<id>` | `jianshanagent-plugin-<id>` | `jianshanagent_plugin_<id>` | `<id>` | `plugin.<id>` |
| 站点插件 · 平台 | 一个 wiki 平台在 MediaWiki 之上多出来的东西 | `site-<平台>` | `jianshanagent-site-<平台>` | `jianshanagent_site_<平台>` | `<平台>` | `site.<平台>` |
| 站点插件 · 站 | 某个平台上的一个站 | `site-<平台>-<站>` | `jianshanagent-site-<平台>-<站>` | `jianshanagent_site_<平台>_<站>` | `<站>` | `site.<站>` |
| 部署插件 | 和机器人一起部署、机器人离了它照样跑的服务 | 在核心的 `deploy/plugins/<id>/` | — | — | `<id>` | Compose 变量（`.env`） |
| 实例 | 一个部署：服务哪个 wiki、用哪些插件的哪个版本 | `instance-<名字>` | — | — | — | 它的 `config/` |
| 模板 | 某一层的最小骨架，新建那一层的仓库时从它复制 | `template-<层>` | 占位的名字 | 占位的名字 | 占位的 id | — |

规矩：

- **id** 只用小写字母、数字、下划线，在同一种插件里不能重。站点插件的 id 是它自己那一级的名字（`yys`），
  不带上级；**层级写在仓库名和包名里**——从最上面一级到自己，依次连起来：
  灰机平台是 `site-huiji` / `jianshanagent_site_huiji`，灰机上的阴阳师 wiki 是
  `site-huiji-yys` / `jianshanagent_site_huiji_yys`。不建在任何平台上的站直接是 `site-<站>`。
- 仓库名、发行包名用连字符，Python 包名用下划线，三者只差这一点。
- 核心自带的功能插件（`chat`、`knowledge`……）不单独成仓库，在核心的 `src/jianshanagent/plugins/<id>/`；
  目录名就是 id。
- 核心的仓库叫 `agent-core`，发行包和 Python 包叫 `jianshanagent`（包名要独一无二，仓库名在组织里已经带着前缀了）。
- 模板仓库里的名字都是占位的：平台 `example`、站 `demo`。从模板建仓库以后要换掉，换法写在各模板的 README 里。
- 现有的仓库：

  | 仓库 | 层 | id |
  |---|---|---|
  | [`agent-core`](https://github.com/JianShanAgent/agent-core) | 核心 | — |
  | [`site-huiji`](https://github.com/JianShanAgent/site-huiji) | 站点插件 · 平台 | `huiji` |
  | [`site-huiji-yys`](https://github.com/JianShanAgent/site-huiji-yys) | 站点插件 · 站 | `yys`（上级 `huiji`） |
  | [`instance-yys`](https://github.com/JianShanAgent/instance-yys) | 实例 | — |
  | [`template-site-platform`](https://github.com/JianShanAgent/template-site-platform) | 模板 · 站点插件 · 平台 | `example` |
  | [`template-site-wiki`](https://github.com/JianShanAgent/template-site-wiki) | 模板 · 站点插件 · 站 | `demo`（上级 `example`） |
  | [`template-instance`](https://github.com/JianShanAgent/template-instance) | 模板 · 实例 | — |

GitHub 的组织里不能给仓库分文件夹，所以靠三样东西分层：

- **名字前缀**：`site-`、`plugin-`、`instance-`、`template-`，列表里同一层的挨在一起。
- **话题标签**：每个仓库都打 `jianshanagent`、`mediawiki`、`qq-bot`，再按层打 `core`、`site-plugin`（平台另加 `platform`）、
  `instance`、`template`（模板同时打它所属那一层的标签）。
- **组织主页**：仓库 `.github` 的 `profile/README.md`，按层列出所有仓库。新建仓库以后在那里加一行。

## 2. 插件的目录

一个插件是一个自成一体的目录（对装成包的插件来说，就是那个 Python 包的目录）：

```
<插件目录>/
  plugin.yaml      清单：它是谁、依赖谁、有什么能力
  config.yaml      默认配置（没有可配的东西就不放）
  configs/         另外带的配置（对话插件的人设在这里）；一般没有
  __init__.py …    代码（部署插件没有代码，是 Compose 片段和它的配置文件）
```

单独成仓库的插件，仓库是这样的：

```
site-huiji-yys/
  README.md                         照第 6 节的格式写
  LICENSE                           MIT
  pyproject.toml                    发行包名、依赖、登记（第 4 节）
  src/jianshanagent_site_huiji_yys/  插件目录（上面那几样）
  tests/                            里面要有规范自检（第 7 节）
  assets/icon.svg
```

## 3. 清单 `plugin.yaml`

不认识的键会报错，免得写错了键名却以为生效了。

```yaml
id: yys                    # 核心自带的和部署插件：和目录名一样；装成包的：和登记的名字一样
kind: site                 # feature / site / deploy
name: 阴阳师 wiki           # 给人看的名字
description: …             # 一两句话说明它管什么（必填）
# 只有站点插件有：
parent: huiji              # 上级的 id；最上面一级不写
capabilities: [wiki, knowledge, extend]
# 只有功能插件有：
after: [knowledge]         # 这些插件也启用时，要排在它们后面
extension_points: [wiki]   # 开给站点插件的扩展点
# 只有部署插件有：
services: [loki, alloy]    # 它的 compose.yaml 里有哪些服务（要和文件里的一致，不能和别的重名）
```

## 4. 让核心找到它

**装成包的插件在自己的 `pyproject.toml` 里登记**（Python 的 entry points：名字是插件 id，值是包路径），
装进同一个 Python 环境就能用，核心不用改：

```toml
[project]
name = "jianshanagent-site-huiji-yys"
dependencies = ["jianshanagent", "jianshanagent-site-huiji"]   # 核心，和它的上级

[project.entry-points."jianshanagent.sites"]       # 功能插件登记到 "jianshanagent.plugins"
yys = "jianshanagent_site_huiji_yys"
```

**启用**是每个部署自己的事，写在实例的 `config/` 里：

| 插件 | 写在哪 | 怎么写 |
|---|---|---|
| 功能插件 | `core.plugins.yaml` 的 `enabled` | 列 id，按加载顺序 |
| 站点插件 | `core.wiki.yaml` 的 `site` | **只写最末一级的 id**（`site: yys`），上级顺着清单自动带出来、先加载；不写就是纯 MediaWiki |
| 部署插件 | 服务器 `shared/.env` 的 `JIANSHANAGENT_DEPLOY_PLUGINS` | 列 id，逗号隔开；一个都不带就留空，这一行不能没有 |

没登记的包也能当站点插件用：`site` 写它的包路径（`mypkg.mysite`）。一个站点插件的包也可以把下级放在自己的
`sites/` 目录里一起带上（清单里的 `parent` 要写它）。

## 5. 各种插件要提供什么

**功能插件**——包里有 `create_plugin()`，返回的对象有 `id`（和清单一样）和 `register(ctx)`
（见 `core/plugin.py`）。可以在清单里开出**扩展点**（`extension_points`）让站点插件往里接东西；
现在有两个：`wiki`（查询，`wiki_query` 开的）、`knowledge`（知识库，`knowledge` 开的）。

**站点插件**——能力（清单的 `capabilities`）只有这几种，写了哪种就得有哪种：

| 能力 | 要有什么 |
|---|---|
| 一个扩展点的名字（`wiki`、`knowledge`） | 包里同名的模块（`wiki.py` 或 `wiki/`），模块里有 `create(setup)`，返回那个扩展点的基类的实例（基类在开出扩展点的功能插件里；`setup` 见 `core/sites.py`）。下级要用上级的东西：`setup.parent(上级的类)` |
| `extend` | 自己 `config.yaml` 里的 `extend` 段：`配置名 → 要并进去的内容`。读配置时就并进去了——名单合在一起，单个值以站点插件给的为准。这个站的清洗规则、提示词里的说法、人设都走这里，所以通用的插件不用知道站点插件的存在 |

**部署插件**——`deploy/plugins/<id>/` 里放 `plugin.yaml`、`compose.yaml`（Compose 片段，和
`deploy/docker-compose.yml` 合在一起用，相对路径从 `deploy/` 算起）、可选的 `init.sh`
（上线前的准备：建数据目录、补 `.env` 里缺的变量；只添不改，能重复执行）和服务自己的配置文件。
它和机器人之间没有代码上的往来：机器人只往标准输出打 JSON 日志，谁来收是部署插件的事。

**配置**怎么分层见 `core/config.py` 开头：包里的默认值 → 站点插件的 `extend` →
实例 `config/` 里的同名文件（只写要改的项）→ 开发机的 `config/local/` → 管理后台里改的。

## 6. 文档怎么写

README 是写给第一次来的人看的。先让人知道它是什么、有了它会怎样，再说怎么用——不要一上来就是字段表。

每个仓库的 README 开头是一样的：图标、仓库名、一句话，再是一行徽章（它是哪一层、id、上级、许可），和一句英文简介。
往下没有固定的章节，但这几样要有：

- **它管什么**：用大白话说，最好有一个看得见的例子（一段对话、一段配置）。
- **怎么用**：装到哪、在配置里怎么点名。
- **配置**：配置名是什么、默认值在哪、一个部署要改时写在哪。
- **开发**：怎么装环境、怎么跑测试，目录里各是什么。
- **许可**。

模板仓库另外要写清楚「复制以后哪几处要一起改名」。

`docs/` 下的文档：文件名用中文短语，第一行是标题，第二段是 `> JianShanAgent · <层> · 文档`。
提交信息、注释、文档都用中文，说清楚「是什么、为什么」；只写现状，不留过去的版本和将来的打算。

## 7. 规范自检

核心带着一个检查函数，每个插件仓库的测试里调一次（`tests/test_conformance.py`）：

```python
from jianshanagent.testing.conformance import check_plugin


def test_conforms_to_the_plugin_spec() -> None:
    check_plugin("jianshanagent_site_huiji_yys")
```

它查的是：登记了没有；包名照没照第 1 节取（站点插件要带着从平台到自己的每一级）；清单读不读得出来、
有没有写 `description`；上级找不找得到；清单里写的能力包里有没有；默认配置是不是合法的 YAML；
仓库里有没有 `README.md` 和 `pyproject.toml`。不合规范时报错会说明哪里不对、该怎么改。

写插件测试时还用得上 `jianshanagent.testing.sites`：在临时目录里搭站点插件、把包登记成插件。

## 8. 换一个 wiki

- **另一个 MediaWiki，不写插件**：用 [`template-instance`](https://github.com/JianShanAgent/template-instance) 建一个实例仓库，
  `config/core.wiki.yaml` 里写 `api_url`、`name`（页面地址不是 `<站点>/wiki/<标题>` 的另写 `article_path`），`site` 不写。
  这样 `/查` 只认页面，知识库只有条目页，提示词里是对什么 wiki 都说得通的说法。
- **让机器人懂这个站自己的东西**：用 [`template-site-wiki`](https://github.com/JianShanAgent/template-site-wiki) 建一个站插件。
  清洗规则、问题分类、提示词里的说法、人设写在它 `config.yaml` 的 `extend` 段里，不用写代码；
  这个站有结构化数据、别名、自己的命令时，再写 `wiki.py`、`knowledge.py`。
- **好几个站建在同一个平台上**：平台共用的接口和约定用 [`template-site-platform`](https://github.com/JianShanAgent/template-site-platform)
  建一个平台插件，各个站的插件在清单里写 `parent`。只有一个站时不需要这一层。
- **另一个灰机 wiki**：装上 `site-huiji`，站插件叫 `site-huiji-<站>`，清单里 `parent: huiji`。
- `site`、wiki 的地址、站点插件配置里的 `extend` 不能在管理后台里改（它们决定加载哪些代码、密钥发到哪里）。
