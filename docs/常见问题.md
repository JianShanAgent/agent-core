# 常见问题

> JianShanAgent · 核心 · 文档

## 起不来

**报「core.llm.yaml 已启用，但没有可用的密钥」**

`config/secrets.yaml` 的 `llm.api_key` 没填，或者还是模板里 `YOUR_` 开头的占位值。填上真的密钥再启动。

**报「不知道是哪个 wiki：core.wiki.yaml 的 wikis 里要写上挂哪些 wiki」，或者「要写 api_url」**

实例的 `config/core.wiki.yaml` 的 `wikis` 名单是空的，或者里面那一项的 `api_url` 没填。填 wiki 的接口地址，一般是 `https://<站点>/api.php`，有的站是 `https://<站点>/w/api.php`。

**报「core.wiki.yaml 最外层的 api_url、site 不用了」**

这是只能挂一个 wiki 时的写法。把 `api_url`、`site_base`、`article_path`、`auth_header`、`site` 挪进 `wikis` 名单的一项里，并给它起个 `id`（写法见核心的 `defaults/core.wiki.yaml`）；`secrets.yaml` 里的 `wiki.authkey` 跟着挪成 `wiki.<id>.authkey`。已经建过知识库的，把知识库目录里的文件挪进 `<知识库目录>/<id>/`；库里原有的内容算主 wiki 的，照常能查，下一次导入时换成标了出处的。

**`docker compose up` 报 `bind source path does not exist: …/config/secrets.yaml`**

还没有从模板复制：`cp config/secrets.example.yaml config/secrets.yaml`，填好再启动。

**`docker compose up` 以后 `qqbot` 一直在重启**

看日志：`docker compose logs qqbot`。多半是上面两条之一。只想先在网页上试、还没有 QQ 凭据，在 `.env` 里写 `JIANSHANAGENT_DRY_RUN=1`。

**在管理后台改了配置以后起不来**

不会。保存时装不起来的改动会自动撤回；真的带着坏配置重启了，启动时也会退回默认值，并在后台页面顶上说明是哪里不对。要手动撤掉某份改动，删掉 `data/config/<配置名>.yaml`。

## 管理后台

**地址是什么**

机器人自己的 HTTP 端口，默认 `http://127.0.0.1:8080`（`app` 配置的 `healthcheck.port`）。用核心的 `./release` 发布到服务器时，默认映射在服务器的 `127.0.0.1:13001`。

**登录令牌在哪，忘了怎么办**

`secrets.yaml` 里写了 `admin.token` 就是它。没写的话第一次启动时自动生成，存在数据目录里：

| 怎么跑的 | 怎么看 |
|---|---|
| `uv run jianshanagent` | `cat data/admin/token` |
| `docker compose` | `docker compose exec qqbot cat /data/admin/token` |
| `./release` 发布到服务器 | 服务器上 `cat <数据目录>/bot/admin/token` |

想换一个：删掉这个文件再重启，会生成新的。

**打开只有一句「管理后台的页面还没有构建」**

后台的页面是构建好放在包里的（`src/jianshanagent/admin/static/`），正常装下来就有。出现这句话说明这个目录被删了或者没装全：从源码运行的话，`cd webui && npm ci && npm run build` 重新构建一次。

**有的配置在页面上是只读的**

接口地址、用哪个密钥、用哪个站点插件、后台自己的开关和端口不能在网页上改，要改文件。原因和名单见 [配置说明](配置说明.md)。

**改了配置没生效**

`app`、`core.storage`、`gateway.qq`、`core.admin` 这四份要重启机器人才生效（「系统信息」页有重启按钮），别的保存后马上生效。Docker 方式下改的是 `config/` 里的文件的话，要重新 `docker compose up -d --build`——配置是构建时拷进镜像的。

## 回答

**一条消息被回复了两次**

同一个 QQ 机器人在两个地方同时在线了。线上的在跑时，本机调试一定要带 `JIANSHANAGENT_DRY_RUN=1`。

**`/查` 能用，随口问的答不了或者答得很泛**

查证工作流要有数据库和知识库。没配数据库时它不生效，对话模型只能自己拿 `/查` 那套工具去查。配好数据库以后，还要把知识库建起来（下一节）。

**回答不对，想知道是哪一步出的问题**

管理后台「查证过程」里点开那一条：分析问题时认出了哪些名字、知识库和站内搜索各拿到什么资料、查证员依据的是哪几条、复核怎么说，都在里面。

**没有嵌入接口的密钥行不行**

能跑。检索只剩关键词这一路，不能以图搜图，也没法给新内容算向量。

## 知识库

**`kbsync` 的日志说「这台机器上还没有知识库的文件」**

自动更新只做增量，不会自己把整个 wiki 从头取一遍。第一次要手动建：

```bash
python -m jianshanagent.plugins.knowledge run      # 取数、清洗、切片
python -m jianshanagent.plugins.knowledge embed    # 算向量
python -m jianshanagent.plugins.knowledge load     # 导入数据库
```

原生运行时前面加 `uv run`，Docker 方式加 `docker compose exec qqbot`。三步都能中断了接着跑。建好以后 `kbsync` 下一轮会自己接手。挂了几个 wiki 时这三步挨个 wiki 做；只建其中一个，在子命令前面加 `--wiki <id>`（`... knowledge --wiki bwiki run`）。

**知识库多久更新一次**

默认每小时看一次 wiki 的最近更改，没有变化时只发 1 个请求，有变化就只重做变了的页面。间隔在 `plugin.knowledge` 的 `sync.interval_minutes`。

**「全部重取」是什么，为什么在夜里**

有的页面是拿公共的数据渲染出来的，数据改了，页面自己并没有新的修订，看最近更改看不出来该重做哪几页。所以留了一个兜底：把渲染的页面全部重取一遍。默认只在 03:00–06:00 做，每 7 天一次；公共数据集改过的话，等改动过去 24 小时以后的第一个夜间时段再做一次（wiki 自己的渲染缓存一天一换，早了取到的还是旧的）。这些都在 `plugin.knowledge` 的 `sync.full_refresh` 里。不想等：`python -m jianshanagent.plugins.knowledge sync --full`。

**自动更新停住了，后台的知识库页说被拦下了**

结果比上一次少了一大截、要新算的向量多得不正常、取数失败的页面太多时，它会停下来不往库里写，每一轮再试。看过确认没问题，手动放行一次：`python -m jianshanagent.plugins.knowledge sync --force`。门槛在 `plugin.knowledge` 的 `sync.limits`。

**换了嵌入接口或者型号**

库里的向量和算它们的接口、型号、维度绑在一起。换了以后旧的向量不能和新算的问题向量比，检索会退回只用关键词；要把知识库和图库的向量全部重算一遍（`embed`、`images embed`），再 `load`、`images load`。

**wiki 在 Cloudflare 后面，取数被拦（403）**

站点给了放行密钥的话：`core.wiki.yaml` 里那个 wiki 的 `auth_header` 写请求头的名字，密钥填在 `secrets.yaml` 的 `wiki.<那个 wiki 的 id>.authkey`。

**能不能把取数调快一点**

别调。那是别人的站点，默认每秒最多 2 个请求、同时最多 2 个。

## 插件

**自己写的插件放在哪**

只给这一个实例用的，放在实例目录里：站点插件 `sites/<id>/`，功能插件 `plugins/<id>/`。目录里要有清单 `plugin.yaml`，清单里的 `id` 要和目录名一样。想给别人用或者几个实例共用的，做成单独的包，见 [插件规范](插件规范.md)。

**放进去了，后台里看不到**

插件是启动时找的，放进去以后要重启机器人。之后：

- 功能插件：在后台「插件」页打开它，或者写进 `config/core.plugins.yaml` 的 `enabled`；
- 站点插件：在 `config/core.wiki.yaml` 的 `wikis` 里，给用它的那个 wiki 写 `site: <id>`（只写最末一级，上级自动带出来）。

**清单里写错了键名**

不认识的键会直接报错并说明是哪个文件的哪一项，不会悄悄不生效。

## 升级

**怎么知道有新版本，怎么更新**

管理后台「系统信息」页最上面的「版本与更新」：主仓库发了新版本，这里会显示版本号和更新说明，侧栏下面也会提一句。`uv` 和 Docker 方式点「更新并重启」就行；`./release` 发布的和从源码运行的只提示，更新办法页面上写着。细节见 [部署与运维](部署与运维.md) 的「核心的更新」。

**点了更新，结果还是原来的版本**

新版本没起来，自动退回了。「版本与更新」里有一条黄色的提示，写着是哪个版本、哪里出的错。

**后台说「新版本的第三方依赖和环境里装的不一样」**

在后台点更新只换核心自己的代码，依赖变了要重建环境：

| 怎么跑的 | 怎么做 |
|---|---|
| `uv run jianshanagent` | `uv sync --upgrade-package jianshanagent`，然后重启 |
| `docker compose` | `docker compose build --no-cache && docker compose up -d` |

实例模板的 `pyproject.toml` 里核心是从 GitHub 的 main 分支装的，这两条命令装上的是 main 上最新的提交。

**「正在用的」和「环境里装的」版本不一样**

正常。在后台点更新装的新版本放在数据目录里（`data/core/`），盖在环境里装的那一份上面。想回到环境里装的版本，点「还原」。

**访问 GitHub 很慢，查不到新版本或者下载不动**

在实例的 `config/core.update.yaml` 里填 `download_prefix`（一个 GitHub 加速服务的地址）可以让下载走镜像。查新版本用的是 GitHub 的接口，查不到时页面上会显示原因，不影响机器人别的功能。

数据库结构的变更在机器人启动时自动执行，不用手动做。

## Docker

**`data/` 目录里的文件要 `sudo` 才能看**

Linux 上是这样的：容器里的机器人以 uid 10001 运行，`data/` 归它。要看里面的东西，用 `docker compose exec qqbot cat /data/...`，或者加 `sudo`。

**`docker compose ps` 里有一个 `init` 是 exited**

正常。它只在启动时跑一下，把 `data/` 交给容器里的用户，然后退出。

**一台机器上放几个实例**

每个实例一个目录，各自 `docker compose up`。项目名和镜像名跟着目录名走，互不相干；只要把 `.env` 里的 `ADMIN_PORT` 错开。
