# 部署与运维

> JianShanAgent · 核心 · 文档

JianShanAgent 支持三种部署运行方式，按你的机器环境与维护习惯任选其一：

1. **Python / `uv` 原生直跑（无需 Docker）**：在安装了 Python 3.12+ 与 `uv` 的机器上（macOS 和 Linux 验证过，Windows 没有测过），在实例仓库目录内执行 `uv sync && uv run jianshanagent` 即可启动机器人与内置 Web 管理后台（端口 `8080`，令牌在 `data/admin/token`）。需要后台每小时自动增量更新知识库时，另起一个守护进程（如 `systemd` / `pm2` / `supervisor`）运行 `uv run python -m jianshanagent.plugins.knowledge sync --loop`。
2. **单机 Docker Compose 一键启动**：在由 [`template-instance`](https://github.com/JianShanAgent/template-instance) 创建的实例仓库目录内，执行 `cp .env.example .env && docker compose up -d --build`，一键拉起 `qqbot`、`kbsync` 与 `postgres`（`pgvector`）三个容器。实例内的 `sites/` 与 `plugins/` 目录直接挂载进容器，`git pull && docker compose restart qqbot kbsync` 即可同步自写插件改动。
3. **生产服务器多版本原子发布（`./release`）**：适合在本地开发机编码、通过 SSH 向远程 Linux 服务器发版，自带多版本归档、健康检查超时自动回滚、每日数据库自动备份与可选的 Loki + Alloy + Grafana 日志采集栈。

下面各节重点说明第 3 种生产多版本发布栈的目录结构、日常发版、增量同步与备份恢复操作。除标明「在服务器上」的命令外，其余均在开发机的**实例仓库**目录内执行。

机器人生产栈由 Docker Compose 编排：

| 服务 | 镜像 | 说明 |
|---|---|---|
| `qqbot` | `jianshanagent-qqbot:<发布号>` | 机器人。健康检查 `http://127.0.0.1:18080/healthz`（只绑本机）；管理后台在 13001 端口，见 [管理后台](管理后台.md) |
| `kbsync` | 同上（同一个镜像，另一个入口） | 知识库自动更新：每小时看一次 wiki 改了什么，只重做变了的部分并导入数据库，见下面「知识库自动更新」 |
| `postgres` | `pgvector/pgvector:0.8.7-pg17` | 对话历史、记忆；带 pgvector 扩展 |
| `backup` | 同上 | 每天 03:30 `pg_dump`，保留 14 天；管理后台改过的配置一起备份；可以再拷一份到另一块盘，见下面「备份和恢复」 |
| `redis` | `redis:7-alpine` | 预留，现在的代码不用它 |

上面五个是机器人离不开的（`deploy/docker-compose.yml`）。另外可拆的服务是**部署插件**，各自一个目录（`deploy/plugins/<id>/`），带哪些写在服务器 `shared/.env` 的 `JIANSHANAGENT_DEPLOY_PLUGINS` 里：

| 部署插件 | 服务和镜像 | 说明 |
|---|---|---|
| `logs`（运行日志） | `loki` `grafana/loki:3.7.9`、`alloy` `grafana/alloy:v1.11.3`、`grafana` `grafana/grafana:13.3.0` | 把各容器打到标准输出的日志收起来存 14 天；Alloy 只采本项目的容器。机器人不知道它们存在 |

Grafana：<http://<服务器地址>:13000>（局域网内直接打开，用户 `admin`，密码在服务器的 `/opt/jianshanagent/shared/.env`）。查日志进「Explore」，数据源选 Loki，例如 `{service="qqbot"}`、`{service="qqbot", level="error"}`。

不想带日志：把 `.env` 里那一行改成 `JIANSHANAGENT_DEPLOY_PLUGINS=`（留空，但这一行要在），再 `./release activate <当前发布号>`，那三个容器就没了，数据留在盘上。想换一套日志系统：照 `deploy/plugins/logs/` 另写一个目录，在名单里换掉 `logs`（怎么写见 [插件规范](插件规范.md)）。

## 核心的更新

主仓库每发一个版本，各个实例的管理后台「系统信息」页会显示「有新版本」和更新说明（机器人每隔几小时看一次主仓库的 Release；不想让它查，把 `core.update` 的 `enabled` 关掉）。怎么更新看是哪种跑法：

| 怎么跑的 | 怎么更新 |
|---|---|
| `uv run jianshanagent` | 后台点「更新并重启」 |
| `docker compose`（实例模板） | 后台点「更新并重启」 |
| `./release` 发布到服务器 | 后台只提示。版本由 `components.lock` 锁定：`agent-core` 里 `git pull`，实例目录里 `./release pin`、提交、`./release deploy` |
| 从源码运行（可编辑安装） | 后台只提示。在源码目录里 `git pull`，重启 |

点「更新并重启」做的事：

1. 从主仓库的 Release 下载那个版本的安装包，核对校验和，检查它能不能用在这个环境里。
2. 解到数据目录下的 `data/core/versions/<版本>/`（容器里是 `/data/core`），记成「待确认」，原地重启机器人。环境里装的那一份不动。
3. 新版本启动完成才算数。起不来（启动时出错，或者连着两次没走到启动完成）就自动退回原来的版本，后台里会显示是哪里出的错。
4. 知识库自动更新（`kbsync`）在下一轮开始前发现版本换了，自己原地重启换过去。

这样装的叫「更新包」：它在数据目录里，盖在环境里装的版本上面，重建容器、重新 `uv sync` 都还在。后台「版本与更新」里能看到正在用的是不是更新包，也可以点「还原」回到环境里装的版本。环境里装的版本追上来以后（重建了镜像，或者 `uv sync --upgrade-package jianshanagent`），更新包自动不再用、被清掉。

更新包只换核心自己的代码。**新版本的第三方依赖有变化时不能这样更新**，后台会说明，要重建环境：

```bash
docker compose build --no-cache && docker compose up -d      # Docker 方式
uv sync --upgrade-package jianshanagent                       # uv 方式，然后重启
```

访问 GitHub 慢的机器：在实例的 `config/core.update.yaml` 里给 `download_prefix` 填一个 GitHub 加速服务的地址（只影响下载安装包；校验和仍然取自 GitHub 的接口，镜像给的文件对不上就不装）。

进程直接退出、没有人把它拉起来的情况（`uv` 方式、没有用进程管理器）：新版本一启动就崩掉的话机器人会停在那里。再启动它，最多两次，它会放弃这个版本、用回原来的。Docker 方式容器会自己重启，不用管。

### 发版（主仓库的维护者）

版本号写在 `pyproject.toml` 里。发一个版本：

```bash
# 1. 改 pyproject.toml 的 version，然后
uv lock                                             # 锁文件里的版本号跟上
cd webui && npm ci && npm run build && cd ..        # 改过页面的话：构建产物是入库的
git commit -am "0.3.1"
# 2. 打带附注的标签——附注就是后台里显示的更新说明——推上去
git tag -a v0.3.1 -m "这一版改了什么……"
git push origin main v0.3.1
```

推上标签以后 GitHub Actions（`.github/workflows/release.yml`）会跑测试、构建页面、打安装包，发出 Release，带 `jianshanagent-0.3.1-py3-none-any.whl` 和 `SHA256SUMS`。标签和 `pyproject.toml` 里的版本对不上时不发。只认 `v0.3.1` 这种纯数字的版本号；预发布的标签不会被当成新版本。

加了或者升了第三方依赖的版本，实例不能在后台直接更新，更新说明里要写明「要重建环境」。

## 服务器上的目录

```
/opt/jianshanagent/
  releases/<发布号>/     每次发布一个目录，内容就是那个提交的代码（不改动）
  current -> releases/…  当前在用的发布
  previous -> releases/… 上一个发布（`release.sh rollback` 切回它）
  activations.log        每次切换记一行：什么时候、从哪个到哪个、成没成
  shared/.env            Compose 变量：数据库密码、数据目录、端口、带哪些部署插件和它们的变量（600，不随发布走）
  shared/secrets.yaml    QQ / wiki / LLM 凭据（属主 10001，600，不随发布走）
  ctl                    compose 入口，用法同 docker compose：ctl ps、ctl logs -f qqbot

/home/jianshanagent/          数据盘（1TB SSD，xfs）上的全部数据
  postgres/  backups/  redis/  bot/      机器人离不开的
  loki/  grafana/  alloy/                部署插件 logs 的
```

同一个机器人不能两处同时在线（一条消息会被回复两次）：服务器上的 `qqbot` 在跑时，不要在开发机上再启动 `jianshanagent`。

## 更新版本

各个仓库的改动提交之后，在实例仓库的目录里：

```bash
./release pin               # 把旁边各个仓库现在的提交记进 components.lock
git commit -am "…"          # 提交实例仓库：发布号就是这个提交的 7 位短号
./release deploy            # 一键将当前提交打包上传、构建镜像并激活上线（起不来自动切回上一个版本）
```

（若想先把镜像传上去构建好、稍后再切换，也可以拆成 `./release push` 和 `./release activate` 两步，不传参数默认操作当前 `HEAD` 提交。）

只改了这个部署的配置或实例自带的 `sites/`、`plugins/` 目录时不用 `pin`，提交了直接 `./release deploy`。

`activate` 在服务器上一口气做完这几步（`deploy/scripts/server-release.sh`）：先让启用的部署插件各自做准备（建数据目录、补 `.env` 里缺的变量），再检查新发布的 Compose 文件连同 `shared/.env` 能不能解析，过不了就停、线上不动 → 让旧版本的机器人和知识库更新先停稳（机器人会等在途的消息答完，最多 20 秒）→ 切换，等有健康检查的服务都健康（最多 3 分钟）→ **起不来就自动切回原来的发布**，打印各服务状态和机器人最后的日志，然后报错 → 起来了就把原来的发布记成 `previous`，并清理旧发布。同一时间只允许一个发布操作，第二个会直接报「另一个发布操作正在进行」。

- 只传各个仓库 git 里那些提交的内容（`components.lock` 里写的），工作区里没提交的改动不会带上去；服务器不需要访问 GitHub。几个仓库要并排放在开发机的同一个目录下。
- 管理后台的页面在 push 时由开发机构建（用核心那个提交里的 `webui/`，要有 Node），产物随发布传上去；只想看能不能构建：`./release webui`。
- 回滚：`./release rollback` 切回上一个；要回到更早的，`./release list` 看有哪些，再 `activate <旧发布号>`。数据库结构的变更不会跟着回滚——迁移都只是加表加列，回滚后的代码不受影响；遇到删改列的迁移，回滚前先看一眼。
- 旧发布的清理：每次切换成功后自动做，留着正在用的、上一个和最新上传的 5 个，其余的目录和镜像一起删（只碰 `releases/` 和 `jianshanagent-qqbot` 这一个镜像仓库）。留几个用环境变量 `JIANSHANAGENT_KEEP_RELEASES` 改，`0` 是不清理；手动清理：`./release prune [留几个]`。
- 换凭据：改好开发机的 `config/secrets.yaml` 后 `./release secrets`，再重启机器人——管理后台「系统」页的重启，或者服务器上 `/opt/jianshanagent/ctl restart qqbot`。
- `config/local/` 是开发机的调试覆写，不会也不应该传到服务器。
- 数据库结构的变更由机器人启动时自动执行（`src/jianshanagent/migrations/`）。
- 切换时备份和部署插件的容器（Loki、Alloy、Grafana）会跟着重建（它们挂载的配置文件在发布目录里），几秒钟；Postgres 和 Redis 只在 Compose 里它们自己的定义有变化时才重建。整个切换机器人不在线半分钟左右，这期间发来的消息平台会在重连后补发。

## 知识库自动更新

知识库（查证用的切片、以图搜图用的图库）是从 wiki 取下来存在库里的，wiki 改了要跟着更新。`kbsync` 服务每小时做一轮（挂了几个 wiki 就轮流做几个，各有各的游标、状态和闸门，一个出了问题不耽误别的）：读 wiki 的最近更改（没有变化时只发这 1 个请求），有变化就重新列页面、只取变了的，给新内容算向量，再导入数据库。机器人不用停，导入完马上生效。做法和各种情况怎么处理写在 `src/jianshanagent/plugins/knowledge/sync.py` 开头，参数在 `plugin.knowledge` 的 `sync` 段（`src/jianshanagent/plugins/knowledge/config.yaml`；管理后台里能改，下一轮生效）；状态在管理后台「知识库 → 概况」里，每个 wiki 一张卡：上次什么时候看过 wiki、更新了什么、有没有被拦下的事。

- **第一次上线前、每新挂一个 wiki 都要拷一次文件**：`kbsync` 只做增量，数据盘上没有某个 wiki 的知识库文件时它对那个 wiki 什么都不做（不会自己把整个 wiki 从头取一遍）。在开发机上运行 `./release kb-seed`，把 `data/kb` 里的切片、向量和取数缓存拷到服务器（不含原图缓存，用不着）；`./release kb-seed <wiki 的 id>` 只拷那一个 wiki 的（`data/kb/<id>/`），别的 wiki 在服务器上的文件不动。
- **对 wiki 的请求量**（每个 wiki）：没变化的一轮 1 个；有变化的一轮通常十几到几十个。每隔几天（或者公共数据集改了满一天以后）夜里 03:00–06:00 把渲染的页面全部重取一遍兜底，400 多个请求、三四分钟。默认每秒最多 2 个请求、同时最多 2 个（站点插件可以给它那个 wiki 定得更慢），一轮有请求数上限，wiki 出故障时连着几个请求不成就整轮收手。
- **闸门**：结果比上一次少了一大截、要新算的向量多得不正常、库里的向量和现在配置的嵌入接口不是同一种……这些情况它停下来不往下做，原因显示在管理后台，每一轮都会再试。看过确实没问题，手动放行一次（见下面的命令）。

```bash
/opt/jianshanagent/ctl logs -f --tail 50 kbsync                                         # 它在做什么
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge sync --status   # 现状（不发请求）
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge sync --plan     # 现在做一轮的话打算做什么（1 个请求，不动任何东西）
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge sync            # 不等下一轮，现在就做一轮
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge sync --full     # 现在就把渲染的页面全部重取（不等到夜里）
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge sync --force    # 这一轮不过闸门
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge --wiki <id> sync --full   # 只做某一个 wiki（--wiki 写在 sync 前面；不写就挨个做）
```

要停掉自动更新：管理后台里把 `plugin.knowledge` 的 `sync.enabled` 关掉（服务空转），或者 `/opt/jianshanagent/ctl stop kbsync`。开发机上也能手动跑同样的命令（`.venv/bin/python -m jianshanagent.plugins.knowledge sync`）：没配数据库时只更新 `data/kb` 里的文件。

## 日常操作（在服务器上）

```bash
/opt/jianshanagent/ctl ps                          # 各服务状态
/opt/jianshanagent/ctl logs -f --tail 100 qqbot    # 看机器人日志
/opt/jianshanagent/ctl restart qqbot               # 重启机器人
curl -s http://127.0.0.1:18080/healthz       # 健康检查
ls -lh /home/jianshanagent/backups/               # 备份文件
/opt/jianshanagent/ctl exec backup bash /usr/local/bin/backup.sh once   # 立即备份一次
```

容器都设了 `restart: unless-stopped`，异常退出会自动重启，服务器重启后随 Docker 自动拉起。各容器都有内存上限（`deploy/docker-compose.yml` 的 `mem_limit`）：这台机器上还有别的项目，哪个容器失控了，被杀掉重启的是它自己。

## 备份和恢复

`backup` 服务每天 03:30 做一次（`deploy/backup/backup.sh`，开头写了每一步）：

- 数据库 `pg_dump` 成 `/home/jianshanagent/backups/jianshanagent-<时间>.dump`，写完把整份文件解一遍确认读得回来；保留 14 天。
- 管理后台里改过的配置（`/home/jianshanagent/bot/config/`，不在数据库里）打成同名的 `.config.tgz`。
- **第二份**：数据库和备份默认在同一块盘上，盘坏了两样一起没。在 `/opt/jianshanagent/shared/.env` 里把 `BACKUP_COPY_DIR`填成另一块盘上的目录，每次备份完会再拷一份过去，那边留最新的 3 份（`BACKUP_COPY_KEEP`）：

  ```bash
  install -d -m 700 -o 999 -g 999 /opt/jianshanagent/backups        # 系统盘上，和数据盘不是同一块
  echo 'BACKUP_COPY_DIR=/opt/jianshanagent/backups' >> /opt/jianshanagent/shared/.env
  /opt/jianshanagent/ctl up -d backup
  ```

  这仍然是同一台机器：机器整个没了（失窃、火灾、误删）两份都在里面。要防这个，得定期把备份拷到别的机器或网盘，现在没有做。
- **有没有成功**：每次的结果记在数据库的 `backup_runs` 表里，管理后台「系统信息」页显示最近一次；超过 26 小时没有成功的备份（`config/core.admin.yaml` 的 `backup_warn_hours`），后台每一页顶上都会有一条提醒，`ctl ps` 里 `backup` 也会显示 unhealthy。没有人打开后台就没有人看到——它不会往 QQ 或别处发消息。
- 不在备份里的：知识库的文件（`/home/jianshanagent/bot/kb/`，能从 wiki 重新取）、日志（Loki，本来只留 14 天）、`shared/.env` 和 `shared/secrets.yaml`（凭据，开发机上有 `config/secrets.yaml`；`.env` 里的数据库密码丢了要重设）。

恢复：

```bash
/opt/jianshanagent/ctl stop qqbot kbsync            # 先停掉连着数据库的服务
ls -lh /home/jianshanagent/backups/                # 挑一份
/opt/jianshanagent/ctl exec backup bash /usr/local/bin/backup.sh restore jianshanagent-<时间>.dump
/opt/jianshanagent/ctl start qqbot kbsync
```

`restore` 先把备份恢复到一个新建的空库里，整份恢复成功之后才和正在用的库对调名字；原来的库改名成 `jianshanagent_before_<时间>` 留着，确认没问题后按它打印的那句命令删掉。中途哪一步失败，正在用的库都没动过。备份比现在的版本旧也没关系：机器人启动时会把之后新增的表结构补上（这段时间里新表的数据自然是没有的）。

恢复之后库里的知识库回到了备份那一刻，而 `kbsync` 以为库里已经是最新的（它记的是「文件导进去过没有」），不会自己再导。所以恢复完手动导一次（把数据盘上各个 wiki 的切片、图片记录和向量导进库，不访问 wiki，可以反复跑）：

```bash
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge load
/opt/jianshanagent/ctl exec kbsync python -m jianshanagent.plugins.knowledge images load
```

不要用 `pg_restore --clean` 直接往正在用的库上盖：备份之后才建的表它不会删，迁移记录却回到了备份时的样子，机器人启动时重跑迁移会报「表已存在」起不来。

后台改过的配置要一起恢复时（会覆盖现在的）：

```bash
tar -xzf /home/jianshanagent/backups/jianshanagent-<时间>.config.tgz -C /home/jianshanagent/bot && chown -R 10001:10001 /home/jianshanagent/bot/config
```

## 在一台新服务器上从头部署

```bash
# 1. 开发机：先把代码传上去并构建镜像（第一次执行前确保服务器已安装 Docker 与 Docker Compose）
./release push
# 2. 服务器：创建数据目录、生成 shared/.env（含随机数据库密码）
#    第二个参数是管理后台监听的网卡地址（如 127.0.0.1 或内网 IP）；第三个参数是部署插件（默认 logs，不带填 ""）
/opt/jianshanagent/releases/<刚才打印的7位短号>/deploy/scripts/server-init.sh /home/jianshanagent 127.0.0.1
# 3. 开发机：上传 secrets.yaml 凭据（有本地知识库缓存可顺带执行 ./release kb-seed），然后直接激活当前提交上线
./release secrets
./release activate
```

迁移到别的机器：停栈（`ctl down`），把 `/opt/jianshanagent/shared/` 和数据目录整个拷过去，再按上面的步骤发布一次即可。

## 服务器拉不动镜像时

有的服务器 `docker pull` 走不通（守护进程的代理访问镜像站会中途断开，而守护进程的配置又不方便动）。这套部署为此做了两件事：

- Compose 里的镜像标签都固定到具体版本，服务器上有了就不再拉；机器人镜像在服务器上本地构建，基础镜像只用 `python:3.12-slim` 一个，依赖从 PyPI 镜像源装（版本和哈希仍以核心的 `uv.lock` 为准）。
- 确实要拉新镜像时，用 `deploy/scripts/fetch-image.py` 绕开守护进程，直接从镜像站下载再导入：

  ```bash
  python3 fetch-image.py docker.m.daocloud.io/pgvector/pgvector:pg17 pgvector/pgvector:pg17 /tmp/pgvector.tar
  docker load -i /tmp/pgvector.tar
  ```
